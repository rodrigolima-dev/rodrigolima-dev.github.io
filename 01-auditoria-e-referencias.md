## Atualização de direção aplicada

Depois desta auditoria, a página passou a usar **E-commerce Application** como nome provisório do produto de e-commerce. Os repositórios públicos ainda mantêm os nomes `orpheuswim-frontend` e `orpheuswim-api`, que continuam sendo a prova do código até o novo nome ser escolhido.

A OpportunusAI foi mantida como projeto e como experiência. O `TechTalk` foi retirado da seleção por ser simples para a narrativa atual. O novo destaque mobile é o HIT, um app de fitness privado em desenvolvimento, incluído somente com o status e a previsão de lançamento informados pelo autor.

## Diagnóstico

A versão atual tem bons sinais de engenharia pública: o dashboard informa que os dados são fictícios; a frase “The server checks the session, organization, and route permissions before returning data” aponta para uma decisão concreta; os repositórios são o destino das ações; e os projetos LangGraph e n8n deixam claro que são exemplos offline. Esses detalhes devem continuar.

O problema editorial principal é a ordem. A primeira tela apresenta “FULL STACK SOFTWARE ENGINEER + APPLIED AI”, “From code to production” e o cargo de cofundador e CTO antes de explicar qual produto o leitor pode abrir. O primeiro case é o dashboard da OpportunusAI, embora a evidência pública mais completa e autoral para uma vaga full stack seja a Orpheuswim: catálogo, seleção, carrinho, API e início do pedido. A seção de abordagem repete os mesmos princípios que aparecem no dashboard e nos fluxos offline. O texto de infraestrutura afirma operações de produção que não são necessárias para o posicionamento pedido e não serão usadas na copy final sem prova específica.

Hipótese editorial adotada: trocar abstrações por um percurso curto de prova. O leitor entende o cargo e a stack na primeira tela, abre a Orpheuswim como case principal, chega ao dashboard técnico em um clique e encontra a atribuição de cofundador somente em Experiência.

## Detalhes bons que estavam escondidos

- O site já informa “public code you can inspect, run, and test”; essa promessa deve ser aplicada ao case certo, com o link do primeiro arquivo.
- O dashboard já diferencia dados fictícios e V2 privada. A nova versão conserva essa distinção e não transforma a imagem em demo.
- O fluxo do carrinho calcula total, conserva itens no localStorage e monta a mensagem com produto, tamanho, cor e quantidade. Esse é o detalhe que faz a Orpheuswim ser entendida por recrutamento e engenharia.
- O projeto Python deixa o preview offline por padrão e exige --apply para chamar embeddings ou escrever no banco. É uma prova melhor que uma lista de “IA aplicada”.
- Guarded Retrieval Graph e n8n já dizem que não têm LLM, credenciais nem chamadas externas. Esses limites tornam os cases técnicos honestos.

### Padrões que vale aproveitar

1. A primeira tela combina cargo, tipo de sistema e um próximo clique claro.
2. O card informa problema ou ação do usuário, depois mostra decisão e prova.
3. A autoria aparece com qualificadores: solo, contribuição, equipe, cliente ou projeto próprio.
4. A prova fica a no máximo dois cliques do projeto: case, arquivo, teste, demo ou repositório.
5. A página nomeia limites; não chama fixture de produção nem um link de WhatsApp de pagamento.

### O que não vale copiar

- A estética de terminal do Erik Cunha torna a navegação menos imediata para quem só precisa entender a função e abrir o código.
- Os números e métricas dos sites de referência são relatos de seus autores; não são um modelo para inventar métricas no portfólio de Rodrigo.
- Os elementos gráficos e personagens do site de João Bernardo são personalidade daquele autor, não evidência de engenharia para este portfólio.
- A lista extensa de projetos e clientes de Brittany Chiang é adequada a um histórico longo; replicá-la desviaria a atenção dos três cases públicos que Rodrigo consegue sustentar agora.

## Por que estas provas foram escolhidas

### Case principal: Orpheuswim

- **Clareza do problema:** há um fluxo visível de catálogo → seleção da peça → carrinho → mensagem de pedido.
- **Autoria identificável:** os dois repositórios públicos são de Rodrigo; o frontend e a API podem ser lidos em conjunto.
- **Profundidade:** React/Vite, React Router, estado persistido do carrinho, Axios, API REST em Java/Spring Boot, JPA/MySQL, JWT e Docker aparecem em arquivos distintos.
- **Inspeção:** Cart.jsx mostra a decisão e a consequência em poucas linhas; ProductController.java mostra a participação da API.
- **Limite honesto:** o código abre o WhatsApp e limpa o carrinho. Não processa pagamento e não prova que uma venda foi concluída.

### Case técnico complementar: OpportunusAI Dashboard

É a melhor prova pública de permissões e isolamento entre organizações. A demonstração usa fixtures, perfis fictícios e APIs de leitura; a V2 privada não deve ser apresentada como demo pública. A copy usa os testes de 401/403, troca de empresa e cache privado, e não promete banco ou produção.

### Outros complementos

- **vector-chunk-kit:** prova Python com preview offline antes de embeddings e banco; testes demonstram determinismo, hashes, idempotência e replacement explícito.
- **Guarded Retrieval Graph:** prova LangGraph/LangChain Core com autorização antes da recuperação, retry lexical limitado e ausência de LLM.
- **n8n Automation Patterns:** prova de workflows inativos, validação estrutural e comportamento determinístico; um teste Node foi executado nesta auditoria.

### Candidato excluído da seleção principal

digital-product-sales-journey foi lido, inclusive docs/ORIGIN.md. O documento identifica a base como estudo guiado da Alura e preserva autoria de módulos de terceiros; Rodrigo descreve uma adaptação arquitetural. É uma prova válida de leitura de arquitetura e de contribuição de integração, mas não deve ser apresentado como sistema comercial autoral sem uma página que delimite cada mudança. Por isso não entra no primeiro conjunto de cards.

## Checagem editorial final

- Um recrutador consegue dizer que Rodrigo é Full Stack Developer e que constrói aplicações web e APIs REST sem mencionar a OpportunusAI? Sim, pela headline e pela Orpheuswim.
- Um líder técnico encontra uma decisão em até dois cliques? Sim: o card liga a Cart.jsx; o dashboard liga ao repositório e ao walkthrough.
- Os botões prometem o destino? Sim: “Abrir case” aponta para a seção; “Ver arquivo” aponta ao arquivo; “Ver repositório” aponta ao GitHub; nenhum botão promete demo não validada.
- Há adjetivo substituindo evidência? Os clichês “scalable”, “from architecture to production”, “modern”, “robust” e “seamless” foram removidos da versão recomendada.
